Glassbox · what, who, why · v0.5.0

Other tools show you what happened.
Glassbox tells you what went wrong.

A one-page brief for anyone deciding whether to try it, share it, or write about it. Local, mechanical, open source. Reads the transcript Claude Code already writes; asks no model for an opinion; sends nothing anywhere.

Whatthe thing

A flight-recorder reader for AI coding sessions

Every Claude Code, Cowork and Agent SDK session writes a .jsonl transcript to ~/.claude/projects/: every prompt, every tool call, every token served, every dollar. Glassbox turns that file into a timeline of every call, a chart of where the context and cost went, and a list of findings — retry loops, tools that kept failing, results that flooded the context, the request that pushed the prompt past 120k tokens and how much of the bill was spent after it. Each finding links to the exact tool calls it is about and ends with one line on what to do differently.

Three ways in. One HTML file you drop a transcript onto (blueprintau.com/glassbox/app); a CLI, npx glassbox-trace, that lists, opens, checks, compares and live-tails sessions; and a Claude Code plugin, /plugin install glassbox@glassbox-trace, that ends every turn with a summary and can hand the findings back to the agent.

No AI in the loop. The rules are thresholds you can read and change, so the same session always gets the same report — which is what lets check --fail-on warn gate a claude -p job in CI the way a test would. Share mode and --redact keep the structure and blank the content, so a screenshot is safe to post.

Whoit is for
The developer who just got a surprising bill

"Why was that so expensive?" is the first question Glassbox answers. Click the cost line, see the request that crossed 120k context, see the screenshots riding along in every request after the tenth.

The team running agents in CI

check --all --since 1h checks every session from the last hour, one line each, exit 1 if any fails. --rates pins a team rate card so everyone's numbers agree.

The person writing or teaching about agents

Compare Sonnet against Opus on the same task, before and after a CLAUDE.md change, the run that worked against the one that didn't — every metric with the change, and the findings only one of them has.

The agent itself

With the plugin's feedback and context options on, the findings go back to Claude, it says what it would do differently, and the next session in that project starts knowing it.

Who built it. Glassbox is a BlueprintAU build from Adelaide, by Aldo Hushi. The brief to the agent was "build a tool your own system would benefit from"; it chose a flight recorder, wrote the design doc, tests and viewer in one session, then loaded that session's own transcript. That trace, sanitised, is the demo inside the tool.

Whyit exists

Because the transcript exists and nobody reads it. The diff shows what the agent changed. It does not show that a tool failed six times, that a subagent re-read the same architecture doc twenty-two times, or that most of the money went on requests carrying 120,000 tokens of context. All of it is already in a file on your disk.

Because the numbers have to be right, and once they weren't. An audit of 33 real sessions found that costs on subagent- and workflow-heavy sessions were badly under-reported: one 8-hour session showed $21.83 when it had cost $322.36. Workflow agent transcripts weren't being read; streamed output-token counts were taken at their first value. Both were fixed in 0.4.2, and the story is told on the site: a cost tool that hides its own mistakes is worthless. The same audit tuned the rules from 481 findings to 142 — a median of two per session, no warnings in the median one — and the audit script ships in the repo so you can run it on yours; it prints counts only.

Because it should be private and boring. No model calls, no tokens spent, no network. The viewer is one file; the CLI has no dependencies; the plugin runs the bundled code with Node. MIT-licensed, source on GitHub.
